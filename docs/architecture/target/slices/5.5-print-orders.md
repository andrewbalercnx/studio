# Slice 5.5 — Print and orders, with Stripe

> **Created**: 2026-11-04 · Phase 5 of `../../REVIEW_PLAN.md`. Plan only; built in three PRs (below).

A locked Book becomes a printed book: the parent picks a print template (Layout), sees the price and
a proof, pays through Stripe (or with print credits), and the order goes to Mixam, after an admin
check if that is switched on. Implements ADR-0010 (immutable renders, orders pin a render) and
ADR-0012 (real payment), and the PrintOrder lifecycle in `../pipeline.md`.

## Owner decisions (2026-11-04)

| Question | Decision |
|----------|----------|
| Stripe | **Test mode first.** Built and run end to end with test keys; live keys later, no code change |
| Shipping | **Included in the price.** One retail price per printed book covers UK standard delivery; UK only, as today |
| Page design | **The existing template system decides.** `printLayouts` already define the page design (one page per story page, or a spread with the picture and the words on facing pages); several templates can be offered, and each declares its own page arithmetic |
| Admin approval | **A system-wide switch.** `config/orders.requireAdminApproval`: on, a paid order waits for an admin to approve it before Mixam; off, it goes straight to Mixam |

## Gaps the survey found

1. **Books have no front or back matter.** `createBook` makes a cover and the story pages only, but
   a print cover needs a back, and `physicalPageCount` already assumes three matter pages.
   **Fix:** Book creation adds a `title` page, an `end` page and a `back` cover, as the old
   storybook pipeline did before #14 deleted it:
   - **Back cover: its own AI art.** The old `story-page-flow` asked the model to design a back-cover
     scene (`generateBackCoverImageScene`: every main character together in a warm, celebratory
     "the story is over" scene, the main child always present, no text in the image) and
     `story-image-flow` drew it with a back-cover prompt. That is ported as a `back` page with its
     own scene, drawn by the same `book.pageArt` job as every other page, in the Book's Style and
     from the Book's cast sheets (not avatars), so it counts in the art progress like the cover.
     The renderer adds the synopsis in the template's back-cover text box.
   - **Title page and end page: typeset, no art**, as before (title, "by {child}"; a closing line).
   - A dedication page waits for a parent-facing input (later).
2. **Two page models disagree.** `physicalPageCount` assumes one printed page per story page;
   spread templates (`leavesPerSpread: 2`) print two. **Fix:** the page count comes from the
   template: `matter + storyPages × leavesPerSpread`, padded to the print product's multiple and
   minimum. A template is offered for a Book only when the result fits the product's maximum.
   The order page shows each compatible template with its page count and price.
3. **Art aspect ratio.** Page art is drawn once, when the Book is made, before any template is
   chosen. The renderer fits art to each template's image box (contain, matching background), so
   one Book can print in any template; a template can declare a preferred ratio for future Books.
4. **Bleed** is defined on products but applied nowhere. The renderer adds the product's bleed to
   every page edge and extends backgrounds into it.

## The model

### Render (ADR-0010)

`book.render` job (queue `render`): input `bookId`, `medium: 'print'`, `layoutId`. It reads the
Book through the same join as `GET /api/books/{id}`, maps pages through the adapter (cover → front
cover; back → back cover; title / end → typeset pages; story → image and text in the template's
boxes), renders cover and interior PDFs (spine width from the page count and the product's paper),
and writes them to `books/{bookId}/renders/{renderId}/{cover,interior}.pdf`. The render document
(immutable) records the template, product, page count, trim size, bleed, file paths, URLs and
checksums. Renders are never overwritten; a new render is a new id.

A print render needs a **locked** Book (content frozen). Starting an order locks the Book, with the
parent's confirmation ("Ordering prints this exact book; you can unlock it later for edits, which
will need a new order").

### PrintOrder

`printOrders/{orderId}`, new shape (`schemaVersion: 2`; the collection was emptied by the reset):
`ownerUid`, `bookId`, `renderId`, `layoutId`, `printProductId`, `productId` / `priceId` (retail),
`quantity`, `amountMinor` / `currency` (charged, VAT included), `payment` (`method: stripe | credit
| admin`, Stripe session and payment ids, refund), `shippingAddress`, `contactEmail`, `status`,
`statusHistory`, Mixam fields, `idempotencyKey`. Server-written only.

```
created ─▶ rendering ─▶ awaiting_payment ─▶ paid ─▶ [awaiting_approval] ─▶ submitting ─▶ submitted
                                │                                                   ─▶ in_production ─▶ shipped ─▶ delivered
                                └▶ cancelled        any paid state not delivered ─▶ cancelled ─▶ refunded
```

`awaiting_approval` appears only while `config/orders.requireAdminApproval` is on. `refunded` comes
only from the Stripe webhook. An admin can mark an order paid only through an audited action.

### Payment (ADR-0012)

- **Price**: a `products` entry linked to the print product, with an active GBP `prices` entry
  (`amountMinor`, VAT and UK delivery included). `externalPriceId` holds the Stripe Price id when
  set; otherwise Checkout uses `price_data` with the same amount. Mixam's cost is never shown.
- **Stripe Checkout**: `POST /api/orders/{id}/checkout` creates a Checkout Session (order id in
  `client_reference_id` and metadata) and returns its URL. The browser goes to Stripe and comes
  back to the order page.
- **Webhook** `POST /api/webhooks/stripe`: verifies the signature, records each event id once
  (`stripeEvents/{eventId}`), and moves the order: `checkout.session.completed` → `paid`;
  `charge.refunded` → `refunded`. Non-200 on internal errors so Stripe retries.
- **Print credits**: `POST /api/orders/{id}/pay-with-credits` spends `print_credit` in the same
  transaction that marks the order paid (`chargeAllowance`, as books do). Credits are granted by
  admins on `/admin/allowances` until credit packs are sold.
- On `paid`: approval on → `awaiting_approval` (admin is emailed); off → an `order.submit` job.

### Submission to Mixam

`order.submit` job (queue `mixam`), idempotent on the order id:

1. Claim `submitting` in a transaction (only from `paid` or `awaiting_approval` + approved).
2. If the order already has a `mixamOrderId`, stop. If a previous attempt may have reached Mixam
   (claimed, no id), look the order up at Mixam by `externalOrderId` first; never submit twice.
3. Build the order document from the pinned render (`mxjdf-builder` with a render adapter) and
   submit; record `mixamOrderId` → `submitted`.

The Mixam webhook then moves the order forward only (`submitted → in_production → shipped →
delivered`); statuses it does not know are logged and change nothing. Parents get emails on
`paid` (confirmation) and `shipped` (with tracking).

### Admin

`/admin/print-orders` keeps its list and detail, now reading the new shape: approve (enqueues
`order.submit`), cancel (refunds through Stripe), audited mark-paid, retry submit (same job, same
key), and refresh status from Mixam. The approval switch lives in Admin → System config.

## Routes (new)

| Route | What it does |
|-------|--------------|
| `GET /api/books/{id}/print-options` | Templates compatible with this Book, each with page count, product and retail price |
| `POST /api/books/{id}/renders` | Start a print render for a template (locks the Book); returns `renderId` |
| `POST /api/orders` | Create an order for a Book + template + quantity + address (idempotency key); starts or reuses the render |
| `GET /api/orders`, `GET /api/orders/{id}` | The family's orders / one order, with timeline and render proof links |
| `POST /api/orders/{id}/checkout` | Stripe Checkout Session |
| `POST /api/orders/{id}/pay-with-credits` | Pay with print credits |
| `POST /api/orders/{id}/cancel` | Parent cancels before submission (refunds if paid) |
| `POST /api/webhooks/stripe` | Stripe events |
| `POST /api/admin/orders/{id}/{approve,cancel,mark-paid,retry,refresh}` | Admin actions (replace `api/admin/print-orders/**` actions) |

## Configuration and secrets

- `stripe` npm package (server only, kept external to the bundle like Cloud Tasks).
- Secret Manager: `STRIPE_SECRET_KEY` (test key first), `STRIPE_WEBHOOK_SECRET`; mounted in
  `apphosting.yaml`.
- `config/orders`: `requireAdminApproval` (default on), `stripeMode` shown in admin
  (test / live, read from the key prefix).
- **Owner, once**: create the Stripe account (test mode), add the two secrets, add the webhook
  endpoint `https://storypic.rcnx.io/api/webhooks/stripe` in the Stripe dashboard
  (`checkout.session.completed`, `charge.refunded`), set retail prices in Admin → Products.

- Non-UK delivery; per-order shipping quotes; VAT breakdowns on invoices (Stripe receipts only).
- A dedication page input; editing page text before printing.
