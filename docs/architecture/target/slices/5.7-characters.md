# Slice 5.7 — Characters and likeness

> **Created**: 2026-11-05 · Phase 5 of `../../REVIEW_PLAN.md`. Plan only; built in two PRs (below).

Children and Characters move onto the server foundations: one schema and repository each, routes on
`withRoute`, and the **Likeness** of ADR-0006 made by jobs on the job runner and the AI harness
instead of fire-and-forget promises inside requests. The browser stops writing these documents.
The rule in `CLAUDE.md` stands: the appearance text is generated from the original photos only.

## The model

```ts
// children/{childId}
type Child = {
  ownerUid: string;
  displayName: string; namePronunciation: string | null; pronouns: string | null;
  dateOfBirth: string | null; description: string | null; likes: string[]; dislikes: string[];
  preferredVoiceId: string | null; autoReadAloud: boolean;
  likeness: Likeness;
  deletedAt: Timestamp | null; deletedBy: string | null;
};

// characters/{characterId}
type Character = {
  ownerUid: string;
  displayName: string; namePronunciation: string | null; pronouns: string | null;
  type: string | null; relationship: string | null; description: string | null;
  likes: string[]; dislikes: string[];
  scope: 'family' | { childId: string };          // today: childId present or absent
  origin: 'parent' | 'story'; originStoryId: string | null;
  usageCount: number; lastUsedAt: Timestamp | null;
  likeness: Likeness;
  deletedAt: Timestamp | null; deletedBy: string | null;
};

type Likeness = {
  photos: string[];                  // Storage paths of the original uploads
  appearance: string | null;         // from photos only (CLAUDE.md)
  portrait: string | null;           // canonical portrait, from photos
  avatar: string | null;             // UI only, never an image-generation likeness
  avatarSource: 'portrait' | 'description' | 'photo' | null;   // 'description' shows "imagined"
  avatarAnimation: string | null;    // UI only
  likenessJob: { describe, portrait, avatar, animate: JobSummary | null };
};
```

`likenessSchema` gains `avatarSource`, `avatarAnimation`, and `avatar` / `animate` job summaries.

## Jobs

| Job | Queue | Runs when | Writes |
|-----|-------|-----------|--------|
| `likeness.describe` | `ai-text` | Photos change; refresh | `likeness.appearance` from up to 3 original photos; cleared when none |
| `likeness.portrait` | `ai-image` | Photos change; refresh | `likeness.portrait` from up to 5 original photos only; cleared when none |
| `likeness.avatar` | `ai-image` | After a portrait, when there is no avatar or the avatar came from an older portrait; on "make a new avatar"; on create with no photos | `likeness.avatar` from the portrait, else drawn from the description (`avatarSource: 'description'`) |
| `likeness.animate` | `ai-image` | After a child's avatar changes | `likeness.avatarAnimation` |

`character.avatar` (#33) becomes `likeness.avatar` with `avatarSource: 'description'`. Each job is
idempotent per input version: the job records the photo set or avatar it was made from and stops
when the entity has moved on (a newer job owns it). Files are stored per job attempt, so a retry
never overwrites a file a document points at. TEST_MODE writes fixtures, as the Book jobs do. Cast
sheets keep reading `portrait` → `photos` → `appearance` (`castSheetSource`), now under the new names.

A parent can still choose one of the photos as the avatar ("use this photo"): `avatarSource:
'photo'`, stored as a copy, still UI only.

## Routes (new)

| Route | What it does |
|-------|--------------|
| `GET /api/children`, `GET /api/children/{id}` | Rebuilt on `withRoute`; owner and persona scope; server-sorted |
| `POST /api/children`, `PATCH /api/children/{id}` | Create / edit profile fields (zod-validated allowlist); create with no photos enqueues `likeness.avatar` |
| `DELETE /api/children/{id}`, `POST /api/children/{id}/restore` | Soft delete and undo |
| `POST /api/children/{id}/photos`, `DELETE /api/children/{id}/photos/{photoId}` | Add (data URL or upload) or remove a photo in one step; enqueue describe + portrait |
| `POST /api/children/{id}/likeness/refresh` | Re-run describe + portrait from the current photos |
| `POST /api/children/{id}/avatar` | `{ source: 'portrait' \| 'description' \| 'photo', photoId? }`: a new avatar (job, or copy for a photo) |
| The same under `/api/characters/**` | Plus `GET /api/characters[?childId=]` for the parent pages |
| `PATCH /api/admin/children/{id}`, `/api/admin/characters/{id}` | Admin owner reassignment (today a browser write) |

Responses carry the likeness and its job states, so the editor shows "describing", "drawing the
portrait", "drawing the avatar" separately, and "imagined" for a description avatar.

## Migration (owner decision: migrate once)

`scripts/migrate-likeness.mjs`, dry run by default, like `reset-trial-data.mjs`: for every child
and character, write `ownerUid` and `likeness` from the old fields, drop picsum and other
placeholder URLs, keep `photos`, and record `likenessMigratedAt`. Idempotent. The code reads only
the new fields from the PR that ships the migration; the deploy note runs the script before that
code goes live. A later PR removes the old fields from the documents and the types.
