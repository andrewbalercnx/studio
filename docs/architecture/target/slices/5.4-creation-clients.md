# Slice 5.4 — Clients on the creation routes

> **Created**: 2026-10-29 · Phase 5, slice 2 (second half) of `../../REVIEW_PLAN.md`.
> Branch `rebuild/phase5-creation-clients`, stacked on 5.1 (#13), 5.2 (#14) and 5.3 (#15).

The web app, the kids PWA and the mobile app create Stories through the routes of
[`5.3-creation-server.md`](5.3-creation-server.md); the retired modes, the session engine, every old
mode route and flow and the old storybook read paths are deleted in the same change, and trial data
is reset at deploy (rebuild-and-delete, `docs/DEPLOYMENT.md` §10).

## What the clients do now

```
mode chooser ── GET /api/creation-modes
   tap ─▶ POST /api/stories {childId, modeId, idempotencyKey}
play view ── web/PWA: listeners on stories/{id} and stories/{id}/turns (ownerUid filter)
             mobile:  GET /api/stories/{id}, polled while finishing
   answer ─▶ POST /api/stories/{id}/turns {input, idempotencyKey}
   finishing ─▶ complete ─▶ Form + Style (BookChooser, slice 5.2) ─▶ POST /api/books
lists and readers ── GET /api/stories?childId, GET /api/stories/{id}
```

- **The latest turn drives the play view**: `promptDisplay`, option `display` and `expects`
  (`choice` buttons; `text` box; `castPick` toggles with the mode's `preselected` suggestions and the
  hero locked in). Free Play and Guided also offer "type your own idea" on choice turns, because
  their engines accept text there. `progress {step, of}` drives "Step N of M" and the strip.
- **Idempotency**: one key per tap. `useCreateStory` keys by (child, mode); `useSendTurn` by
  (prompt index, answer), so a double tap or "Try again" repeats the key and the server records the
  turn once. A second tap while the first request runs is ignored. After an answer is recorded the
  view waits for a newer prompt from the listener, so an old prompt's buttons never answer the next
  question.
- **Errors** (kid-safe copy in `kidSafeMessage`): 409 `TURN_IN_PROGRESS` → wait (1.5 s, 3 s, 5 s, 8 s)
  and repeat the same key; 409 `TURN_CONFLICT` / `STORY_NOT_CREATING` → no retry of the old answer,
  the listener shows the newest turn; 503 `AI_UNAVAILABLE` / `AI_BAD_OUTPUT` and network errors →
  "Try again" with the same key; 402 `ENTITLEMENT_LIMIT` → the server's child-friendly message.
- **Finishing**: `finishing` shows progress, `failed` offers `POST /api/stories/{id}/finish`,
  `complete` opens the Form + Style chooser (toast "Story Complete!"). The ✕ in the play view asks
  before `POST /api/stories/{id}/abandon`; the back arrow keeps the Story, which the lists show as
  "Still being made" with "Keep going".
- **No client writes** to `stories` or `turns` anywhere; the only client write left on these pages
  is the child's `autoReadAloud` preference on the parent-owned child profile (unchanged).

## Decisions where the brief left a choice

| Topic | Decision |
|-------|----------|
| Story rename by the parent | **Dropped** (smaller than a route): the title comes from the mode's hint or `story.finish`. The inline title editor and its client write are deleted |
| GET routes | `GET /api/stories/{id}` returns the Story and its turns (mobile plays through it; the readers use it) and `GET /api/stories?childId` the list, both through `withRoute` with owner + persona checks. Texts are rendered with names on the server (`renderForReader`: `[[cast:id]]` and any model token form, resolved within the owner's family) |
| Which modes the chooser offers | `GET /api/creation-modes`: `live` and `enabledForKids`, for every caller — the chooser is a child surface on every client (as `kids-generators` was). Exactly one `recommended` among the offered modes. Creation itself still applies `modeAvailability` (5.3) |
| Lists | From the API (server status and rendered titles), not listeners: titles may carry tokens, and names are resolved on the server. Abandoned Stories are left out by the server |
| Web play view | Listeners (owner-read rules), as the brief asked; the POST responses are not used to render, only to decide errors |
| Mobile play view | API only (as mobile is today): load `GET /api/stories/{id}` after each answer; poll every 2.5 s while `finishing` |
| Mobile books | The old-storybook screens are removed with the data; My Books says books live in the web app until the app reads Books (clients phase) |
| Read aloud | Browser speech for the web readers; the compile-time story audio (`story-audio-flow`) is gone with compile. Mobile shows text only |
| The kids PWA's api-client context | Deleted: the kids pages use the shared components and `src/lib/stories/api.ts`, which also ends the cold-deep-link crash of `useRequiredApiClient` |

## E2E

The blocking funnel now goes signup → child → kids lock → mode chooser → Story Wizard →
`POST /api/stories` → four TEST_MODE questions answered in the UI → `story.finish` → Form + Style →
`POST /api/books` → reader → My Books → My Stories → story reader. Nothing is seeded for the Story.
Report-only journeys seed a complete Story in the server's shape. See `docs/testing/e2e.md`.

## Known gaps

- Mobile reads no Books (web only) and has no read-aloud; Books in the app come with Phase 6.
- Story-introduced characters have no avatar (Characters slice).
- The kept print/order/share code still references the old storybook model (print slice).
- `help-sample-data` still seeds sessions and a legacy-shaped help story.
- `GET /api/creation-modes` offers the same list to parents and children (kid modes only); a parent-
  only mode (e.g. adventure without `enabledForKids`) has no chooser entry.
